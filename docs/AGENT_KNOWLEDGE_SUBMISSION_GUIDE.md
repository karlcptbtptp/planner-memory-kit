# 本地智能体知识识别与投稿指南

本文件给接入项目里的本地 AI / Agent 使用。目标是让智能体知道：什么算知识、什么时候应该沉淀为本地个人知识、什么内容可由自动化任务提交到 MCP 团队记忆库、哪些内容不能上传。

## 一句话原则

只有“以后会复用、能帮助别人少走弯路、经过基本验证、边界说得清”的内容，才值得进入团队候选队列。

过程、闲聊、临时猜想、未验证的中间结果，不要直接上传为团队知识。

默认规则：本地新知识先进入个人知识池；定期自动化任务再筛选、脱敏、去重，并把合格内容作为候选上传 LS / MCP。

## 什么是知识

一条合格知识至少满足 4 个条件：

| 条件 | 判断问题 |
|---|---|
| 可复用 | 以后遇到类似任务时，还会用到吗？ |
| 有结论 | 它是否给出了明确判断、方法、口径、边界或踩坑提醒？ |
| 有上下文 | 它是否说明适用项目、适用场景、证据来源和限制？ |
| 可搜索 | 标题、摘要、标签是否能让未来 AI 用关键词找回？ |

## 应该先沉淀到本地个人知识池的内容

以下内容默认先写本地，不直接上传：

- 当前项目内刚形成的新结论。
- 本机 AI 通过对话、分析、排障形成的经验。
- 用户个人偏好和工作习惯。
- 未脱敏但可能有价值的草稿。
- 需要进一步确认项目范围或证据的知识。
- 需要和 LS 旧知识对比后再判断是否上传的内容。

## 可由自动化筛选上传的内容

### 1. 稳定结论

适合上传为 `knowledge_items`。

例如：

- 某个数据口径最终确认应该用哪张表、哪个字段、什么过滤条件。
- 某个线上问题排查后确认根因。
- 某个配置机制、玩法机制、活动机制被解释清楚。
- 某个工具链的正确使用路径已经跑通。

必填信息：

- 结论是什么。
- 适用什么项目 / 系统 / 场景。
- 证据来自哪里。
- 下次遇到什么问题应该想起它。
- 有什么边界或例外。

### 2. 可复用流程

适合上传为 `knowledge_items`，必要时后续晋升为原则。

例如：

- “充值下滑”应按数据口径、流量、入口、商品、支付链路排查。
- “新对话启动”应先生成任务记忆包再回答复杂问题。
- “MCP 团队记忆同步”必须先 dry-run 再落地。

### 3. 踩坑和修复方式

适合上传为 `knowledge_items`。

例如：

- Windows 下 npm 参数会被误解析。
- 某个字段名看起来像总值，其实不是总威力。
- 某个工具必须绕过 shell 包装器，否则内容会截断。

内容必须包含：

- 现象。
- 根因。
- 正确做法。
- 如何验证修复。

### 4. 决策记录

适合上传为 `knowledge_items`。

例如：

- 本地 SQLite 继续做 AI 高速缓存，MCP 远端做团队事实源。
- 飞书从主库降级为 legacy / 通知 / 文档协作层。

内容必须包含：

- 选择了什么。
- 放弃了什么。
- 为什么这样选。
- 什么时候需要重新评估。

### 5. 原则候选

适合上传为 `principle_candidates`，不能直接写正式 `principles`。

原则候选通常具有这些特征：

- 跨项目长期有效。
- 会影响多个 Agent 或多个策划的默认行为。
- 不是一次性事实，而是未来反复执行的规则。
- 需要维护人确认后才能强约束团队。

例子：

- “未审核知识不得进入默认 AI 缓存。”
- “本机只回传聚合 usage，不上传原始对话。”
- “原则候选必须有人类维护人审核后才能进入正式原则表。”

## 不应该上传的内容

| 类型 | 处理方式 |
|---|---|
| 闲聊、情绪、口头确认 | 不上传 |
| 未验证猜想 | 留在本地工作区或作为待验证问题 |
| 一次性过程日志 | 不上传，除非提炼成踩坑或流程 |
| 原始 SQL 结果明细 | 只上传聚合结论和口径 |
| 单用户隐私、账号明细 | 不上传 |
| token、cookie、密码、连接串、Webhook | 禁止上传 |
| `99_runtime/`、浏览器登录态、截图缓存 | 禁止上传 |
| 只对本人有用的偏好 | 写入个人记忆，不进团队库 |
| 标注 `do_not_upload`、`local_only`、`personal_only`、`禁止同步` | 禁止上传 |
| 已明显过期的旧口径 | 记录 correction 或 frozen 建议，不作为新知识上传 |

## 什么时候上传

本地智能体在以下时机应先沉淀本地个人知识，随后由自动化任务考虑提交团队候选：

1. 完成一个明确分析任务，并得到可复用结论。
2. 排查一个线上问题，并确认根因或排查路径。
3. 解决一个技术/工具/流程坑，并找到稳定修复方式。
4. 用户明确纠正了旧口径或偏好，且该纠正以后会复用。
5. 形成一个跨对话、跨 Agent 或跨项目都应遵守的规则。
6. 发现本地知识库中有重复、矛盾、旧版被新版替代，并形成整理建议。
7. 发布或更新了团队工具包、runbook、流程图、模板。

不要在这些时机提交团队候选：

- 任务刚开始，还没有结论。
- 只有搜索结果，没有判断。
- 只是把用户原话复制了一遍，没有蒸馏。
- 内容涉及敏感信息，尚未脱敏。
- 你不确定它是否属于当前项目或全项目。

## 自动化上传前自检

自动化任务上传前必须逐项自检：

| 检查项 | 通过标准 |
|---|---|
| 标题 | 18-40 字，包含对象 + 结论 + 边界 |
| 摘要 | 60-120 字，说明以后什么任务该想起 |
| 正文 | 包含结论、适用场景、证据、边界、下次怎么用 |
| 标签 | 4-8 个，包含项目 / 系统 / 场景 / 对象 / 类型 |
| 项目范围 | 明确是当前项目、指定项目、全项目还是个人 |
| 来源 | 能追踪到对话、报告、runbook、提交、文档或任务 |
| 敏感性 | 不含凭据、隐私、原始明细或运行态路径 |
| 重复性 | 搜过本地缓存，确认不是已有知识的重复版本 |
| LS 对比 | 查过 LS 已同步缓存，确认不是团队库已有知识的重复版本 |
| 上传标记 | 没有 `do_not_upload`、`local_only`、`personal_only`、`禁止同步` |
| 状态预期 | 知道上传后只是候选，不能立刻当团队事实 |

## 普通知识投稿模板

自动化任务使用 MCP 工具 `memory.submit_knowledge`。

推荐载荷：

```json
{
  "title": "对象 + 结论 + 边界",
  "summary": "说明以后什么任务该想起这条知识，以及最重要的结论。",
  "content": "结论：...\n适用场景：...\n证据：...\n边界：...\n下次怎么用：...",
  "source_type": "analysis|incident|runbook|conversation|tooling|decision",
  "source_ref": "对话ID、报告路径、Git提交、飞书文档或本地runbook路径",
  "project_id": "giftWeb",
  "actor_id": "local-agent",
  "tags": ["项目", "系统", "场景", "对象", "类型"],
  "clearance": "internal",
  "status": "pending_review"
}
```

注意：

- `status` 默认只能是 `unreviewed` 或 `pending_review`。
- 本地智能体和自动化任务都不能把自己提交的知识直接设为 `accepted`。
- 如果不确定项目范围，提交为当前项目候选，并在正文里说明“不确定是否全项目适用”。

## 原则候选投稿模板

自动化任务使用 MCP 工具 `memory.submit_principle_candidate`。

推荐载荷：

```json
{
  "title": "原则名称",
  "content": "原则：...\n为什么重要：...\n适用范围：...\n例外：...\n违反风险：...",
  "evidence_refs": [
    "支持这个原则的对话、报告、事故复盘、runbook 或 Git 提交"
  ],
  "proposed_by": "local-agent",
  "project_id": "all-projects",
  "status": "pending"
}
```

只有维护人审核通过后，原则候选才能进入正式 `principles`。

## 只记录本地，不上传团队库

以下内容应优先写本地个人知识池或本地 usage，不进入团队库：

- 用户个人偏好。
- 本机路径、个人工具快捷方式。
- 尚未脱敏的分析材料。
- 未完成的工作草稿。
- 当前对话临时上下文。
- 只对本轮任务有用的 pin。

本地记录方式：

```powershell
npm run memory:usage -- record --id 123 --type adopt --source manual --note "用于本次分析"
npm run memory:task -- miss "<应该想起的关键词>" --note "本轮未召回"
```

## 上传后的处理

上传后，本地智能体必须遵守：

1. 投稿只是候选，不是团队事实。
2. 在维护人审核前，不把它写入默认 `team-memory.md`。
3. 不用它覆盖本地已审核知识。
4. 如果它修正了旧知识，给旧知识记录 `correction` 或提交冻结建议。
5. 下次同步 MCP 时，只有远端返回 `accepted` 或 `active principle`，才进入本地默认召回。

## LS 知识使用反馈

从 LS 同步到本地的知识，在使用后需要回传聚合反馈，帮助 LS 做迭代。

应回传：

- 这条 LS 知识被召回了多少次。
- 是否被实际采纳用于回答、分析或决策。
- 是否被召回但没有帮助。
- 是否发生 miss：用户指出“知识库里有但没想起”。
- 是否被纠错：过期、误导、和新事实冲突。
- 是否缺少召回词、摘要或项目标签。

不回传：

- 原始对话。
- 用户隐私。
- SQL 明细。
- 本机文件路径和运行态材料。

## 质量分级建议

| 等级 | 判断 |
|---|---|
| 高 | 结论清楚、有证据、多人/多项目可复用、边界明确 |
| 中 | 当前项目可复用，但证据或边界还需要维护人补充 |
| 低 | 有线索价值，但更像过程记录、单次任务或待验证问题 |
| 垃圾 | 无结论、不可搜索、重复、过期、含敏感信息 |

## 示例

### 好的普通知识

标题：

```text
MCP团队记忆同步必须先dry-run再落地
```

摘要：

```text
当项目接入 MCP 团队记忆库时，本机同步必须先 dry-run 检查 accepted、skipped 和项目隔离结果，确认无误后才能写入本地 SQLite 和 team-memory.md。
```

正文：

```text
结论：MCP 团队记忆同步必须先 dry-run，再真实落地。
适用场景：任意项目第一次接入团队记忆库、切换 project_id、调整 clearance 或同步规则后。
证据：同步规则会过滤未审核、冻结、其它项目和权限不足知识；dry-run 能提前看到 accepted/skipped。
边界：紧急修复也不能跳过敏感内容扫描。
下次怎么用：先执行 memory:sync:mcp -- --project <项目> --dry-run，确认项目隔离正确后再去掉 dry-run。
```

### 不好的投稿

```text
今天试了一下同步，好像可以。
```

问题：

- 没有对象。
- 没有结论。
- 没有证据。
- 不知道以后什么任务该想起。
- 不能指导别人操作。
